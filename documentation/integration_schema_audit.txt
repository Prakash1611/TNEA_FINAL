11. INTEGRATION RISKS AND EVIDENCE
-----------------------------------

Risk 1 - Same column names, different measures
Evidence: all non-missing matched category values differ between the two
files. The fields are cutoff marks versus rank values.
Why it matters: a blind merge or overwrite could destroy one measure or make
rank values appear to be cutoff values.
Safe handling: merge with explicit suffixes or rename only in the integrated
output, for example cutoff_oc and rank_oc. Do not modify source files.

Risk 2 - Branch-name formatting mismatch
Evidence: 249 matched rows differ only for AG: uppercase cutoff name versus
title-case rank name.
Why it matters: joining on branch_name would create false unmatched rows.
Safe handling: use branch_code as the key; optionally normalize display names
in a derived integrated output after retaining original source names.

Risk 3 - Historical college-name variants
Evidence: year 2024, college code 1511 has five name variants in each file.
Why it matters: joining on college_name can split one college into multiple
values or create false mismatches.
Safe handling: use college_code, retain source names, and document any future
college-code changes with an explicit mapping table.

Risk 4 - Incomplete category values
Evidence: both files contain category missing values; rank and cutoff
missingness differs by 17 category cells.
Why it matters: missing is not equivalent to zero, and a missing value must not
be imputed from the other dataset without source evidence.
Safe handling: preserve missing values independently for cutoff and rank;
retain partial indicators; validate any later imputation separately.

Risk 5 - Less-specific keys are repeated
Evidence: year + college_code has 2,183 groups for 16,174 rows, and year +
branch_code has 510 groups for 16,174 rows.
Why it matters: either key alone would create one-to-many or many-to-many
matches.
Safe handling: include year, college_code, and branch_code together and assert
uniqueness on both sides before joining.

Risk 6 - Column order differs
Evidence: year is first in cutoff and last in rank.
Why it matters: positional assumptions could misread columns.
Safe handling: join and validate by explicit column names, never by position.

12. PROPOSED INTEGRATION PLAN
-----------------------------

Candidate join key:
(year, college_code, branch_code)

Expected relationship:
One cutoff record to one rank record for the current five-year files.

Direct merge safety:
- Key-level merge: structurally safe after uniqueness assertions; all 16,174
  keys match one-to-one.
- Blind direct merge: not safe, because the files contain overlapping column
  names with different semantics and one known branch-name casing mismatch.

Normalization requirement:
- No key normalization is currently required: year, college_code, and
  branch_code already have matching types and value sets.
- Do not normalize source files as part of integration.
- Any display-name normalization should occur only in a derived output and
  should preserve original names.

Mapping-table requirement:
- No college-code or branch-code mapping table is required for these current
  files because all code sets match exactly.
- A future historical mapping table is recommended if later source years show
  college-code changes or branch-code remapping.

Recommended integrated layout:
Keep the current wide row grain and add source-specific names for overlapping
measures, for example cutoff_oc/rank_oc through cutoff_st/rank_st. Retain the
partial indicators with clear source semantics, or retain one shared indicator
only after verifying the exact business meaning. Do not stack cutoff and rank
into a single category value. A long category table may be useful later for a
separate analytical view, but it is not necessary for the initial safe join.
